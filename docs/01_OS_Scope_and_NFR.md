# 01. StudyOS: границы системы и нефункциональные требования

## 1. Название и концепция

**StudyOS** — учебная операционная система на Python с монолитным ядром.
Оболочка (shell) работает в пространстве пользователя и обращается к ядру только
через системные вызовы. Ядро управляет процессами, памятью, файловой системой и
пользователями. Роль «диска» выполняет база данных SQLite (`db/os.sqlite`):
таблица `files` — файловая система, `processes` — реестр процессов,
`users` — пользователи, `syscalls_log` — журнал системных вызовов.

## 2. Границы системы

### Входит в StudyOS (реализуется)

| Подсистема | Что реализуется |
|---|---|
| Управление процессами | создание (`sys_exec`), список (`sys_ps`), завершение (`sys_kill`), состояния new → ready → running → waiting → terminated, планировщик Round Robin |
| Управление памятью | выделение и освобождение памяти страницами по 4 КБ, лимит памяти на систему |
| Файловая система | файлы и каталоги в таблице `files`: создание, чтение, удаление, список |
| Пользователи и права | вход/выход, роли `user` и `admin`, пароли в виде SHA-256 |
| Журналирование | каждый системный вызов записывается в `syscalls_log`, ошибки ядра — в `logs/kernel.log` |
| Командная оболочка | цикл команд `help, echo, users, whoami, login, create, ls, ps, exit` |

### Не входит в StudyOS (имитируется заглушками или не делается)

| Функция | Обоснование |
|---|---|
| Работа с реальным оборудованием (CPU, RAM, диск) | Python работает поверх настоящей ОС, прямого доступа к железу нет; диск заменён SQLite |
| Прерывания и драйверы устройств | требуют программирования на уровне ассемблера/C; таймер, клавиатура, диск и экран — заглушки |
| Настоящая виртуальная память и MMU | аппаратная трансляция адресов недоступна; память считается логически (счётчик страниц) |
| Сетевые протоколы (TCP/IP) | большой объём работы, не относится к теме; за время практики не реализовать |
| Внешние службы каталогов (LDAP, AD) | пользователи хранятся локально в таблице `users` |
| Графический интерфейс | тема проекта — ядро и системные вызовы, достаточно текстовой оболочки |
| Многопользовательская одновременная работа | один терминал; параллельный доступ к SQLite дал бы блокировки |

## 3. Сценарии использования

**Роли:** пользователь (`user`) — работает со своими файлами и процессами;
администратор (`admin`) — полные права, управление пользователями и системой;
система — фоновые процессы ядра (планировщик, очистка памяти).

| № | Сценарий | Роль | Системные вызовы | Модули |
|---|---|---|---|---|
| 1 | Вход в систему | пользователь | `sys_login` | shell → syscalls → kernel → auth → db (`users`) |
| 2 | Создание файла | пользователь | `sys_create_file` | shell → syscalls → kernel → fs → db (`files`, `syscalls_log`) |
| 3 | Чтение файла | пользователь | `sys_read_file` | shell → syscalls → kernel → fs (проверка прав) → db |
| 4 | Список файлов | пользователь | `sys_list_files` | shell → syscalls → kernel → fs → db |
| 5 | Запуск процесса | пользователь | `sys_exec`, `sys_mem_alloc` | shell → syscalls → kernel → memory, scheduler → db (`processes`) |
| 6 | Список процессов | пользователь | `sys_ps` | shell → syscalls → kernel → scheduler → db |
| 7 | Завершение процесса | admin / владелец | `sys_kill` | shell → syscalls → kernel → scheduler, memory (освобождение) → db |
| 8 | Просмотр журнала вызовов | admin | `sys_logs` | shell → syscalls → kernel → db (`syscalls_log`) |
| 9 | Удаление файла | владелец / admin | `sys_delete_file` | shell → syscalls → kernel → auth (права) → fs → db |
| 10 | Завершение работы ОС | admin | `sys_ps`, `sys_kill`, `sys_shutdown` | shell → syscalls → kernel → scheduler → db |

Пример подробно (сценарий 2): пользователь вводит `create` и путь → оболочка
вызывает `sys_create_file(path, content)` → ядро проверяет, что пользователь
авторизован и имеет право писать в каталог → модуль `fs` добавляет строку в
`files` → ядро записывает вызов в `syscalls_log` → оболочка выводит id файла.

## 4. Нефункциональные требования

| Код | Категория | Требование | Метрика / способ проверки |
|---|---|---|---|
| NFR-P1 | Производительность | обработка одного системного вызова | ≤ 50 мс, замер `time.perf_counter()` в `kernel.execute` |
| NFR-P2 | Производительность | одновременных процессов | не менее 10 (`config.MAX_PROCESSES`) |
| NFR-P3 | Производительность | запуск оболочки (загрузка ядра и БД) | ≤ 1 с |
| NFR-P4 | Производительность | `sys_ps` при 10 процессах | ≤ 20 мс |
| NFR-R1 | Надёжность | ошибка в процессе/вызове (деление на ноль и т. п.) не роняет ядро | исключение перехватывается, статус `ERROR` в журнале; тест `test_kernel_survives_error` |
| NFR-R2 | Надёжность | запрос памяти сверх лимита 64 МБ | отказ (`-1`), процесс не создаётся, запись в журнал |
| NFR-R3 | Надёжность | база создаётся автоматически при первом запуске | `init_db()` вызывается при `boot()` |
| NFR-R4 | Надёжность | 11-й процесс сверх лимита | отклоняется с сообщением, остальные работают |
| NFR-S1 | Безопасность | пароли хранятся только как SHA-256 хэш | в `users.password_hash` 64 hex-символа; тест `test_password_is_hashed` |
| NFR-S2 | Безопасность | пользователь не может удалить/изменить файлы admin | `sys_delete_file` от `user` на файл admin → `False` |
| NFR-S3 | Безопасность | каждый вызов журналируется: имя, аргументы, пользователь, статус, время | 100 % вызовов есть в `syscalls_log` |
| NFR-S4 | Безопасность | гость (`guest`) не может создавать файлы и процессы | вызов от `guest` → отказ |
| NFR-M1 | Поддерживаемость | код разбит на модули по задачам | shell, syscalls, kernel, db, config, (scheduler, memory, fs, auth) |
| NFR-M2 | Поддерживаемость | размер модуля | ≤ 300 строк (`wc -l src/*.py`) |
| NFR-M3 | Поддерживаемость | настройки и лимиты в одном месте | только `src/config.py` |
| NFR-E1 | Ресурсоёмкость | работает на стандартном Python 3.10+ | без `pip install`, только стандартная библиотека |
| NFR-E2 | Ресурсоёмкость | без отдельного сервера СУБД | SQLite — один файл `db/os.sqlite` |
| NFR-E3 | Ресурсоёмкость | размер базы при обычной работе | ≤ 10 МБ |

## 5. Анализ рисков

| № | Риск | Стратегия минимизации |
|---|---|---|
| 1 | Нехватка времени, не успеть всё | приоритеты: ядро и БД → файловая система и оболочка → дополнительные функции |
| 2 | Блокировки SQLite при частых обращениях | одно соединение на операцию, короткие транзакции, без параллельных потоков |
| 3 | Сложная отладка системных вызовов | сквозное логирование: `syscalls_log` + `logs/kernel.log` |
| 4 | Забытая обработка ошибок | чек-лист: в каждом модуле есть `try/except`, ядро вызывает через `kernel.execute` |
| 5 | Потеря целостного представления о проекте | документация в `docs/` и сверка с ней перед каждым днём |
| 6 | Нарушение архитектуры (оболочка лезет в БД напрямую) | правило «стрелки только сверху вниз», ревью импортов |
| 7 | Пароли в открытом виде в БД | хэширование SHA-256 с первого дня, тест на хэш |
| 8 | Рост `os.sqlite` и журнала | `*.sqlite` и логи в `.gitignore`, очистка журнала командой администратора |

## 6. Прототип

| Модуль | Что делает | Как проверить |
|---|---|---|
| `src/config.py` | пути (`DB_PATH`, `LOG_DIR`) и лимиты из NFR | импортируется остальными модулями |
| `src/db.py` | `get_connection()`, `init_db()` — 4 таблицы и администратор (пароль хэширован) | `python src/db.py` → появился `db/os.sqlite` |
| `src/kernel.py` | `boot()`, `execute()` — перехват ошибок и замер времени, `hash_password()`, журнал `logs/kernel.log` | `python -m src.kernel` |
| `src/syscalls.py` | `log_syscall()`, `sys_echo`, `sys_get_users` и заглушки вызовов из docs/02 | `python -m src.syscalls` → записи в `syscalls_log` |
| `src/shell.py` | баннер, цикл команд `help, echo, users, whoami, login, create, ls, ps, exit` | `python -m src.shell` |
| `tests/test_prototype.py` | 5 проверок прототипа | `python -m unittest discover -s tests -v` |

Администратор по умолчанию: логин `admin`, пароль `admin` (в базе — только хэш).

## 7. Словарь терминов

| Термин | Определение |
|---|---|
| Ядро (kernel) | часть ОС, постоянно находящаяся в памяти и управляющая всеми ресурсами |
| Пространство ядра (Kernel Space) | защищённая область памяти, доступная только модулям ядра |
| Пространство пользователя (User Space) | область, где работают прикладные программы и оболочка |
| Системный вызов | интерфейс, через который программа просит ядро выполнить привилегированную операцию |
| Процесс | программа в момент выполнения со своим состоянием, памятью и ресурсами |
| Поток | лёгкая единица выполнения внутри процесса, разделяющая его адресное пространство |
| Планировщик | модуль ядра, выбирающий, какой процесс выполняется в данный момент |
| Дескриптор | числовой идентификатор открытого файла, через который идут чтение и запись |
| Виртуальная память | механизм, при котором адреса процесса транслируются ядром в физические |
| Страница | блок памяти фиксированного размера (4 КБ), минимальная единица выделения |
| Хэширование | необратимое преобразование данных (пароля) в строку фиксированной длины, например SHA-256 |
| Аутентификация | проверка подлинности пользователя (логин и пароль) |
| Авторизация | определение, какие действия разрешены пользователю |
| Монолитное ядро | архитектура, где все подсистемы ядра работают в одном адресном пространстве |
